# ADR-0006: Service-generated UUID v7 identifiers

Status: Accepted

Date: 2026-11-19

## Context

Events and competitors need identifiers that consumers use in URLs. Create writes several rows in one transaction (the event and its competitor links), and all of them need the event ID.

## Decision

- Events and competitors get a UUID version 7 generated by the service, before the database write.
- Sports keep their stable code as identifier ([ADR-0003](0003-sports-and-competitors.md)).
- Consumers address events and competitors by this ID. IDs of external data providers are a separate topic and are not decided here.

## Alternatives considered

- Database sequence. Rejected: the ID is unknown before the insert, sequential numbers reveal data volume and can be enumerated, and merging data from several systems is harder.
- UUID version 4. Rejected: fully random values scatter inserts across the index. Version 7 is time-ordered, so new rows go to the end.
- Provider-supplied IDs as the primary key. Rejected: the service would depend on the format and uniqueness of each provider.

## Consequences

- The service can prepare all rows of a transaction up front.
- IDs are not guessable in sequence.
- A UUID v7 reveals its creation time. This is acceptable for public schedule data.
- At about 5 million rows ([ADR-0001](0001-load-assumptions.md)), the index benefit of v7 over v4 is small. v7 is chosen as a sound default, not because this volume requires it.
- The domain code uses branded ID types, so an event ID cannot be passed where a competitor ID is expected.
