# ADR-0025: Zod for schemas at every boundary

Status: Accepted, amended by [ADR-0034](0034-validation-boundaries.md)

Date: 2026-11-19

## Context

Untrusted data enters the service at three boundaries: HTTP requests ([ADR-0024](0024-fastify.md)), rows read from the database ([ADR-0023](0023-kysely.md)) and environment configuration. At each one a raw value must become a checked domain value, for example a string must become a UTC instant ([ADR-0005](0005-time-in-utc.md)) or a typed identifier ([ADR-0006](0006-identifiers.md)).

## Decision

- Zod describes and validates data at all three boundaries.
- A schema validates and converts in one step: the output type of a route schema is the domain type, not the raw string.
- Route schemas written in Zod are the source for Fastify validation, handler types and the OpenAPI description.
- Zod is not used inside the domain. Domain types are plain TypeScript; their constructors enforce invariants. Zod schemas at the boundary call those constructors.

## Alternatives considered

- TypeBox. It produces JSON Schema directly and is the native companion of Fastify, so OpenAPI needs no conversion. Rejected: converting values into domain types is limited, so validation and conversion would be two steps in two places.
- Hand-written validation functions. Rejected: types, runtime checks and documentation would be three copies to keep in sync.
- Validation by classes and decorators. Rejected: it ties boundary types to classes and decorators without a benefit here.

## Consequences

- One library and one style for input, database rows and configuration.
- OpenAPI is produced through a conversion from Zod schemas. A Zod feature that has no JSON Schema equivalent must be given an explicit description. An API test checks real responses against the generated description.
- A corrupt database row fails validation in the mapper and becomes a typed error, not a wrong domain object.
- Invalid configuration stops the service at startup with a clear message.
